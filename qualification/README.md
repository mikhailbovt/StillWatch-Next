# StillWatch Next release qualification

The [acceptance matrix](../docs/acceptance.md) maps the implementation to its checks. Fast RC v3 Short defines the current native protocol. Archived measurements apply to their original builds and workloads.

## Frozen acceptance inputs

For comparisons built from extracted Git archives, give each source variant an empty `CARGO_TARGET_DIR`. Archived files can have modification times older than an existing Cargo fingerprint. In a Windows worker comparison this caused the control build to reuse a worker from an earlier experiment. Record the resulting worker digests and check that each starts with the declared model pack before measuring it. [Cargo freshness checks](https://doc.rust-lang.org/stable/nightly-rustc/cargo/compiler/fingerprint/index.html#mtime-comparison)

- [Native qualification](fast-rc-v2.json) fixes the 180-minute stage budget, the isolated 60-minute load interval, the nominal source and wall cadence tests, and the required completed fault counts. At 5/2 fps, a full 60-second wall window requires at least 285 pose and 114 fire results per camera. Source-clock floors remain 4 pose and 1.5 fire fps over ten source seconds.
- The runner records elapsed time with `CLOCK_MONOTONIC_RAW` on Linux and QueryPerformanceCounter on Windows. Quiet observations retain the Core-compatible monotonic stamps and the UTC endpoints separately. The validator also measures accepted result cadence across the independent elapsed samples. Earlier quiet traces without recorded clock identity leave the interval incomplete during revalidation. Other observed violations remain visible.
- A native process identity consists of its PID and the OS process start time. Linux uses kernel start ticks from `/proc/pid/stat` so a wall-clock correction leaves the process identity stable. Windows uses the process creation timestamp. [Linux process start field](https://man7.org/linux/man-pages/man5/proc_pid_stat.5.html)
- [Profile schema](schemas/profile-v2.schema.json) binds a workload to a candidate, the three acceptance contracts, host, runtime roles and budgets. Freeze the allowed shapes, source manifest, fault schedule and recovery limits before each run. At qualification, the report must cover the exact binaries, models, operating system, driver and workload. A four-camera CPU profile and a 16-camera profile require separate evidence.
- The production execution profile uses `stillwatch-execution-v1`. The runner and validator independently check its digest, host, Core runtime thread count, capture decoder, binaries, model roles and workload against the frozen inputs. Earlier `schema_version: 1` records support diagnostic runs with mixed source sizes and leave the release verdict incomplete.
- [Report schema](schemas/report-v2.schema.json) defines the validator's output. The validator derives each criterion from the pinned inputs and evidence. An observed gate violation takes precedence over incomplete coverage.
- The run manifest records the Python version and the SHA-256 of each benchmark and end-to-end Python source. The runner checks these files again at seal time. A source change during the run leaves release coverage incomplete.
- [Quality contract](quality-contract.json) freezes the first-cycle quality gates. The site budget is eight false Reviews per day across 16 cameras. The independent Urgent budget is at most 0.001 false Urgents per camera-hour. Timely fire and fall Review targets are 95% within eight seconds, with independent strata and separately measured urgent decisions. These are product acceptance targets chosen for this plan, not measured accuracy or industry standards.
- Dataset v2 scoring resamples linked scene, camera, session, subject and original recording groups with the frozen seed and replicate count. It reports percentile intervals for timely recall and verified negative opening rates when at least two eligible groups exist. The intervals describe variation within the available scenes. Retain the Poisson upper bound and its independence assumptions when evaluating rare false alarms.
- For native model replay against a profile with a fixed Tokio worker count, pass `--core-runtime-threads` to `evaluate.py`. The evaluator probes the exact Core binary, uses that count in the replay and records it alongside the backend and ORT threads.
- [Release obligations](release-requirements.json) lists all 17 criteria from §23.1 and the owners and evidence for G1–G5. A release requires both the applicable native reports and the remaining release evidence.
- [Observation parity v1](observation-parity-v1.json) requires exact CPU preprocessing and one-to-one same-class comparisons on frozen RGB fixtures. Displacement is limited to a quarter pixel and 0.1% of the image axis. The score and joint confidence caps are 0.001. Histogram L1 of 0.02 permits redistribution of at most 1% of normalized bin mass. All locked tensor thresholds remain in force.
- The model warmup gate includes the staged manifest and requires ModelPack v3. Its role identifiers, policy, observation specification and shape inventory must match the run. Version 2 run traces remain useful for calibration. Their manually supplied warm shapes leave the model contract gate incomplete.
- A profile with `models.cuda_graph` enables CUDA Graph capture on one or two inference workers for one declared tensor shape matching the analysis sources. Each worker has its own device input and output buffers for the two active roles and warms that shape before readiness. Numeric and observation checks exercise both captured roles on locked RGB fixtures. The warmup test compares the worker's observations and Fire proposals over the same frames in both CUDA modes.
- Each live canary records the immutable host observation time of the opening frame. A fault trial requires that observation after the fault began and before the incident was committed. The same requirement applies to the steady load interval and to the point when storage pressure is released. Reports missing that provenance keep the affected criteria incomplete.
- The fault and final canaries download a current overview through the paired receiver. The collector matches the incident, packet version and source epoch, checks the packet SHA-256 against the response, and decodes the JPEG. The validator opens the archived image and checks its incident binding, size and digest. Historical run bundles retain the evidence scope recorded by their collector.
- A viewer fault can declare `quiet_source_ms` alongside `require_quiet_before_fault`. The collector records successive accepted Fire observations at native timestamps from the same epoch. A gap, a skipped observation or visible fire or smoke restarts the window. The viewer recovery deadline begins after this precondition.
- The quiet-load media check follows each viewer's decoded frame counter through the full interval, including session renewal. A period with no frame progress beyond the profile's viewer recovery budget fails the check.
- The steady collector records the HTTP status and reason for each failed JPEG check. If the interval stops early, the report links the partial failure inventory and keeps the hour incomplete. A malformed age header or corrupt JPEG contributes a measured snapshot failure.
- Preflight requires a clean source revision in the candidate manifest. It directly invokes the three diagnostic-only commands and verifies that the release Core and worker reject them. Earlier help-only traces lack this check.

## Evaluation inputs and interpretation

Use [the development corpus index](../models/evaluations/development-corpora.json) to reproduce the known misses. Its pinned historical manifests keep their original labels and digests. The [dataset schema](schemas/dataset-v2.schema.json) records source permissions, normalized ROI, last-negative and first-visible timestamps, scene/camera/session, subject linkage and the original segment digests. Related footage and subjects stay in one split. Reserve independent sources until the candidate and thresholds are frozen. The current corpus index contains development material.

The replay evaluator validates version 2 manifests before opening media. Each episode uses its clip's hazard category. A group, scene, camera, session, subject or original media digest stays in one split. Reuse the source and lineage IDs across manifests for each original recording, scene and subject. The evaluator checks the holdout against the known media digests and source-scoped lineage in the development index and its pinned manifests. This catches previously evaluated sources with a different crop or filename when their lineage has been recorded.

Each evaluation group measures one hazard category. Its rate uses the exposure verified by that task. Within each hazard category, a holdout must use distinct clip digests and nonoverlapping source intervals. Cuts from a single original can touch at the same native microsecond and retain the same recording lineage. A grounded negative clip needs measured task coverage with a known camera and a coherent source epoch. Missing scope leaves the time unknown and flags the clip below the coverage floor.

The Fire backend diagnostic compares the same decoded frames at a fixed sampling phase. With version 2 annotations it records the first Review in each annotated region using the quality contract's overlap threshold. It also records the first Review anywhere in the frame. The diagnostic runs the detector and policy without the storage and notification stages.

The evaluator reads the region and track facts of the exact observation that opened a Core incident. Later updates cannot move that region. For medical clips, `subject_frames` gives every visible subject's normalized rectangle at an exact native timestamp in microseconds relative to the first decoded frame. A medical opening receives an annotated subject only when the tracked region uniquely overlaps one subject at that timestamp and the local track reports clear identity. That same frame supplies the reference rectangle for the medical episode match. The report retains the local tracker ID so the match can be reviewed.

Fire annotations can specify `visible_target` as `smoke` or `flame`. The opening must overlap the labeled region and the corresponding visibility flag must be true in that same observation. A flame-only opening on a bright doorway leaves an annotated smoke episode unmatched. Missing visibility facts in otherwise matching archived openings leave the result unverified. Annotations without this field use the existing fire-category match.

The optional legacy replay checks the checkout and both dependency and model locks against `baseline.json`. The report joins the first legacy candidate reference to its captured trace. For medical candidates it uses the exact pose observation with a matching track and confirmed association. Legacy openings retain the `legacy_candidate` label. A trace with usable native timestamps and per-task inference calls supplies measured source-time intervals.

Run `tools/benchmark/evaluate.py` with `--cuda-device` to measure the selected CUDA runtime. Add `--cuda-graph-shape HEIGHT WIDTH` for the single-shape CUDA Graph profile. The evaluator waits for the configured workers before adding replay sources and records the library digests and backend in the report. Its 40 ms wait between polling rounds provides several chances to observe each accepted result at 5 Hz. Coverage still uses the measured source timestamps and acceptance counters.

Use `--slot-receipts` for short diagnostic replays with a compatible Core. The evaluator saves ordered task, policy and incident receipts beside the report and checks them against Core's counters and committed opening rows. The frame identifier joins detections and policy decisions to their task outcome. Coverage measures the fraction of accepted base slots in the applicable source window and separately bounds the gaps between accepted frames. Additional live checks carry no base slot. For a manual Core run, `--analysis-receipts` creates `analysis-receipts.jsonl` in the service data directory with a 32 MiB cap. Use a fresh test directory for each run. The file contains camera identifiers, detected regions and tracking metadata. Use the separate Fire worker diagnostic to inspect the bounded pre-threshold proposals.

For a deterministic Fire comparison, `tools/benchmark/compare_fire_backends.py` sends the same decoded RGB samples and PTS to both CPU and CUDA. Its hash-pinned window file can specify a `phase_offset_us` inside one sample period for each clip. The output lists the selected source timestamps. Add `--cuda-graph-shape HEIGHT WIDTH` to include CUDA Graph and check its observations and proposals against ordinary CUDA, as well as the detector-to-policy decisions against CPU. Supply a separately built diagnostic Core with `trace-fire-policy` enabled for this comparison.

An onset interval starts at the last labeled negative and ends at the first visible frame. For each event, score the window from the negative bound minus the declared pre-onset tolerance to eight seconds after the first visible frame. An episode already visible at the beginning is reported as a reaction from clip start. A short follow-up is reported as censored, with any observed opening retained. An opening needs the matching camera, epoch and spatial annotation before it can count as a hit in a grounded corpus. Medical qualification also requires verified subject identity.

Report nominal, verified and unknown exposure separately. A gap in a version 2 positive window yields `invalid_coverage` even when a spatially matched opening remains in the report. For a version 2 episode already visible at the start, reaction time uses the matched opening. Negative events during gaps remain in the event inventory. Rust snapshots conservatively bound source-time coverage with accepted task timestamps and counters. Legacy aggregate counters leave coverage unknown. Replay measures source decision time and its recorded UTC time. Commit and delivery latency require separately correlated timestamps from native runs.

Report observed rates with numerators, denominators and independent sessions. Use a scene or recording-session block bootstrap for comparisons and label binomial or Poisson intervals that assume independent observations. A conservative confidence bound must meet the threshold for a population claim. Mark the claim incomplete when the cohort, follow-up or verified exposure is insufficient. [NIST proportion confidence intervals](https://www.itl.nist.gov/div898/software/dataplot/refman1/auxillar/propconf.htm)

The evaluator reports per-hour incident openings inside verified negative exposure, with a one-sided Poisson upper bound under the independent-count assumption. It keeps openings from gaps or other epochs in the full negative inventory. These rates describe opening attention levels on the evaluated recording. [Exact Poisson limits](https://wonder.cdc.gov/controller/pdf/FayFeuerConfidenceIntervals.pdf)

With zero false openings and independent observations, the 95% upper rate is `-ln(0.05) / verified_camera_hours`. The current limits correspond to at least 143.80 verified camera-hours for Review and 2,995.74 for an enabled, reachable Urgent policy in this best case. False openings raise the exposure required. Report the number of distinct sites and sessions alongside this calculation. Replaying the same footage on two runtimes measures platform agreement on a single exposure. [Quality thresholds](quality-contract.json)

Run the scoring regressions with `python -B -m unittest discover -s tools/benchmark -p 'test_*.py'`. The evaluator accepts `--rescore` to check immutable openings against their exact frozen manifest. Native replay runs also record coverage.

For a local fall investigation, pass `--slot-receipts --pose-observations` to `tools/benchmark/evaluate.py`. Core writes the PoseBalanced graph and runtime digests in the receipt header. Match Pose policy rows to accepted task receipts on camera, epoch, scene revision, capture generation, frame and source timestamp. Each row records confirmed boxes, COCO-17 keypoints and uncertain associations. Tentative poses are attached to the frame when the tracker confirms them. Start a new history on a scope change or a `long_gap_reset`. The evaluator also exports one paired `.pose.jsonl` and `.pose.receipt.json` per source for the Training Pack identity binder. The export uses accepted current-frame detections in pixel coordinates and keeps tentative history in the original trace. The sidecar binds the video, model, provider, runtime and trace. Review physical identities and retain uncertainty and history boundaries when binding each person chain.

The diagnostic example `fall_features` exposes the Rust input tensor for `stillwatch-causal-pose-v2`. Compare it with the SHA-pinned Python Training Pack extractor on native pose receipts using `tools/benchmark/verify_fall_features.py`. The comparison checks all 128 channels on the causal 21-step grid and checks the selected source PTS. Keep physical identity and event-quality evidence with the reviewed annotations.

## Run native qualification

Stage the native payload and freeze its `manifest.json`, allowed model profiles, workload, media sources and fault schedule before running. Freeze hashes with the `sha256:` prefix. Prepare the qualification Python environment in advance. It uses `jsonschema` for schema checks and `psutil`, `aiortc` and `av` for native load and media measurements. The separate masked WHEP end-to-end test uses NumPy to check decoded pixels. The Core payload runs independently of this environment. Run `python tools/benchmark/prepare_logic.py --output LOGICAL_TEST_BINARIES.json` from the staged candidate’s source revision before the qualification clock starts. Keep its adjacent `.programs` directory so a later Cargo build can run without changing those executables.

Capture the staged Core's `--execution-host` output and the staged worker's `capture-doctor` output as JSON. Freeze a Core-readable profile for the declared RTSP/TCP codec, image size and nominal frame rate. Use the same CUDA device and raw-frame budget in both commands when applicable.

~~~text
python tools/benchmark/prepare_execution.py --candidate PAYLOAD/manifest.json --profile PROFILE.json --source-manifest SOURCES.json --execution-host HOST.json --capture-doctor DECODER.json --output FROZEN
~~~

Use `FROZEN/profile.json` and `FROZEN/execution.json` below. The collector uses the Core runtime thread count from the host probe and configures the same publisher slots, viewer slots, snapshot limit and storage settings during the native run. A release-qualified report is required to activate the execution profile in Core.

Pass `--event-parity EVENT_PARITY.json` to carry measured model regressions into preflight and the logical stage. The ledger holds `candidate_digest`, `profile_digest`, `policy_version` and a `cases` array. Each case uses an ID from the quality contract and records the frozen `reference` and measured `observed` results as JSON objects. Its `evidence` array lists the source artifacts as `path` and `digest` pairs, with paths relative to the ledger and SHA-256 digests prefixed by `sha256:`. Keep the native trace or replay result used to derive each observation. The collector freezes the ledger and the listed source files. The validator checks both stages against that copy and compares values exactly. Missing cases, empty results and results without source files leave the gate incomplete. The ledger carries regression results and supplies no independent corpus or live-delivery evidence on its own.

~~~text
python tools/benchmark/fast_rc.py --protocol fast-rc-v3-short --candidate PAYLOAD/manifest.json --profile PROFILE.json --execution-profile EXECUTION_PROFILE.json --logic-test-binaries LOGICAL_TEST_BINARIES.json --node NODE --demo CREDITED_DEMO.mp4 --fixture-ffmpeg FFmpeg --source-manifest SOURCES.json --fault-schedule FAULTS.json --address TEST_INTERFACE --isolated --output FRESH_RUN_DIRECTORY
~~~

The runner atomically replaces `run-manifest.json` after freezing inputs and after recording each completed proof. It marks those snapshots interrupted until the final seal. To inspect a run after an abrupt stop, execute `python tools/benchmark/validate_report.py RUN_DIRECTORY`. It checks the preserved proofs and leaves unfinished cases unqualified. The immutable raw logs can also contain observations from the interrupted stage. Start each repeat in a fresh output directory.

An input source manifest contains `sources`, `viewers` and `canaries`. Each source declares `id`, a local `file` relative to the manifest, its `digest`, `codec`, `width`, `height`, `fps`, `phase` and `delay_s`. The collector confirms the media’s geometry and decodes the stream through Core. Viewer entries name their `camera` and `profile` (`preview` or `detail`). Canary entries bind a camera and category to a source timestamp range. The fault schedule uses an array of `faults` containing the `id`, `kind`, `camera` and a `canary` with the `source_epoch` and time range. Contiguous RTSP entries with the same `batch` run as a single group of camera interruptions. Every completed cycle needs usable native analysis, a matching live incident with persisted evidence and a receipt from the paired test receiver. Pin the final fresh fixture event as `final_canary` with the same canary fields. It verifies active Pose and Fire on every declared camera, a new persisted live incident and receipt, and SQLite integrity.

A source can include `canary_media` with the relative `file` and `digest` of a clip with a scheduled event for recovery. The fault, storage recovery and final-canary collectors use that clip. Capacity and quiet load use the primary clip. Both files must match the same declared codec, dimensions and frame rate. The one frozen source manifest pins both files, and each stage checks that its active camera fixtures use distinct digests.

For a camera with a separate RTSP main stream, put its `file`, `digest`, `codec`, `width`, `height` and `fps` in the camera’s `detail` object and schedule a detail viewer. The collector publishes both streams, reserves a separate decoder in the execution profile, and checks the viewer’s decoded frame dimensions against the main stream and Core’s encoder scale.

Inference restart cycles record the process identity before and after the fault. Completion requires one replaced inference worker, an observed interruption of analysis on a still-streaming camera, and fresh Pose and Fire progress on every declared camera. The churn collector records usage after each recovered fault and during decoded WHEP sessions. It counts known processes that survive outside the current Core tree and checks both PID and creation time. After the last fault it disables the fixture cameras and verifies capture and media leases, the SQLite writer, queued semantic jobs and surviving children. Retained incident, artifact and receipt totals are recorded separately.

For Core restarts, the collector records a second resource sample 20 seconds after spawning the replacement Core. The validator pairs it with the immediate recovery sample by case, process and native start time. It allows half a second for collection. Core restart growth uses the paired 20-second samples. The report retains the immediate recovery growth for comparison and includes every observation in the peak resource check. A recovery after the sampling window leaves restart growth evidence incomplete.

Churn growth requires at least three complete 60-second blocks with measurements for each required fault kind. A full RTSP schedule spans 15 minutes between the first and last injections to obtain a longer RSS trend. Core restart injections span 20 minutes. The paired sampling series must span at least 19 minutes. The inference restart and viewer fault schedules span at least four minutes. Recovery deadlines start at injection. The report retains the sample count, the number of complete blocks and the projected growth within the frozen resource budget.

Set `resolve_before_fault` for a fixture that repeats a positive scene while preserving its source epoch. The collector records how many previous matching incidents it resolves through the Core API before the cycle starts. Each completed cycle still requires a new incident and device receipt after the fault.

For a viewer cycle, `require_quiet_before_fault` waits for fresh analysis with zero smoke and fire regions. When the case also requests resolution, the collector resolves prior incidents at the first quiet sample. A case with `quiet_source_ms` must observe that duration across consecutive accepted Fire results before it issues the viewer grant. The readiness wait counts against the stage deadline. The viewer’s recovery clock starts with the new session. The validator checks the quiet evidence and requires a new persisted incident and device receipt within the viewer deadline.

Reserve the host for the entire performance run. Use a distinct evidence directory outside the staged payload. Bind TLS and ICE to an assigned private test interface outside loopback. The collector files are inputs to the verdict. `validate_report.py` issues the verdict after verifying their digests, profile and report structure and the measured gates. A selected `--stage` or `--diagnostic-load-seconds` can produce evidence that helps debug a future run. Both protocols require continuous steady load with all declared cameras and decoded media. The v2 interval lasts 60 minutes. Cadence gates use rolling windows contained within the measured interval. The startup observations remain in the raw trace. Openings, result counts, wall observation times, and source or virtual coverage have separate fields.

For a Linux CUDA candidate, pass `--cuda-ort` to `deploy/packaging/stage.py` and provide the extracted ONNX Runtime archive named in `models/native-deps.lock.json` under the supplied native directory. The manifest includes the chosen ONNX Runtime and both providers. Supply authorized CUDA and cuDNN libraries to the staged worker through `STILLWATCH_CUDA_LIB_DIR`. VRAM samples use the selected device's total in-use memory from `nvidia-smi`, including driver and display allocations. The collector checks the driver and total memory against the frozen host fingerprint. Keep other CUDA workloads off the measured device.

The run returns `0` for `PASS`, `1` for `FAIL` and `2` for `INCOMPLETE`. To inspect a sealed run again, validate it into a new filename.

~~~text
python tools/benchmark/validate_report.py FRESH_RUN_DIRECTORY --output REVALIDATED_REPORT.json
~~~

For a native Linux blob-pressure check, add `--blob-enospc` on a runner allowed to create a private mount namespace. Freeze `storage_enospc.pressure_canary` and `storage_enospc.recovered_canary` in the fault schedule. They use the same format as the final canary and identify distinct source epochs on one camera. The collector fills a 4 MiB temporary filesystem mounted only at the fixture blob directory. SQLite stays on the writable parent volume. It records the failed evidence write, frees the space and repeats the pinned live source in a new epoch. Recovery requires a new incident, a device receipt, matching blob hashes and clean SQLite checks.

On Windows, attach an empty writable test volume with at most 4 MiB of usable capacity. Run the collector as administrator and pass its drive root with `--blob-enospc-volume E:/`. Windows mounts the volume on the fixture's blob directory while SQLite stays on the temporary directory's NTFS volume. The collector confirms a native disk-full write and detaches the mounted folder after the trial. The test volume retains the recovered JPEG evidence.

The `storage_database` schedule accepts two fresh canaries in the same format under `sqlite_busy` and `pinned_wal`. These cases keep the declared cameras streaming while the Core writer encounters a real SQLite lock or a reader pins the WAL past 16 MiB. After release, each case checks idempotent retry, fresh source and inference progress, a new live incident, persisted blobs and a device receipt. The combined storage pipeline criterion also requires the isolated blob-pressure case from the same run.

## Fast RC v3 Short

Read the packaged Core's actual `--analysis-policy-version` and pin that version in the profile and model pack before collecting evidence. Set `protocol` to `fast-rc-v3-short` when freezing a new [Short profile](schemas/profile-v3-short.schema.json). Freeze `budgets.short_growth_bytes` for steady load and each of the four fault kinds before starting. Provide limits in bytes for RSS and, on CUDA, for VRAM. Pin a fault schedule with at least 48 RTSP reconnects, eight inference worker replacements, six Core restarts and 24 viewer cycles. The [Short contract](fast-rc-v3-short.json) defines the required camera distribution, maximum batch sizes and stage deadlines.

Prepare the execution profile with the same command above and pass `--protocol fast-rc-v3-short` to the runner. Use an isolated host and allow 12 minutes of continuous steady load after warmup. The collector checks WHEP renewal at minutes 3, 6 and 9 and verifies authenticated JPEGs on both sides of a real access-token rotation. Resource growth uses the first and last complete minutes or the first and last three comparable fault samples. After a Core restart, the matched resource sample is taken 20 seconds after every declared camera resumes analysis. The v2 timing and extrapolation rules continue to apply to v2 reports.

The [Short report schema](schemas/report-v3-short.schema.json) retains all 32 native criteria and limits the result to finite engineering qualification of the frozen profile. A diagnostic load run provides component data. Keep physical deployment, independent event quality, release signatures and production Firebase evidence with their respective acceptance records.

Use the [physical device run sheet](device-run.md) for the observations that require phones, cameras, or external networks.
